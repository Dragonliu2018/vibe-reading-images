Doris 表锁死锁案例可视化

PR #45045 要根治的问题：公平读写锁下，两个线程以相反顺序获取读锁，且 A、B 各有一个写锁排队时，形成四节点循环等待。

① 死锁形成时序

T1 先锁 A 再锁 B，T2 先锁 B 再锁 A。T3 请求 A 的写锁、T4 请求 B 的写锁。 公平锁（hasQueuedPredecessors）让写锁排队阻塞后续读锁—— T1 的 RL(B) 被 T4 挡住，T2 的 RL(A) 被 T3 挡住，而 T3 等 T1 释放 A、T4 等 T2 释放 B，四者成环。

T1 读持有 A T2 读持有 B T3 写等待 A T4 写等待 B 读锁阻塞

② 资源等待环（死锁的充要条件）

等待图中有向边 X→Y 表示「X 等 Y 推进」。T1 等 T4 排队走完，T4 等 T2 释放 B， T2 等 T3 走完，T3 等 T1 释放 A——四节点全部在环内。写者不是「催化者」，而是环上的必要节点： 没有写者排队，读者之间互不阻塞，环不成立。

为什么必须有两个写者？ 只有一个写者（如只有 T3）时，T1 请求 RL(B) 不被阻塞——B 的等待队列空， hasQueuedPredecessors() 返回 false，T1 立即拿到 B、完成、释放 A，环断开。 单写者只能堵住环的一侧。

③ 解法：按 table id 升序加锁，环被切断

PR #45045 规定所有线程都以 table id 升序获取锁。设 id(A) < id(B)， 则 T1、T2 都先请求 A 再请求 B。先到者拿到 A 并继续拿 B；后到者在 A 上排队但不持有任何锁—— 「持有并等待」的前提被打破，循环无法形成。

代码落地：StatementContext.lock() 用 PriorityQueue + Comparator.comparing(TableIf::getId) 把三类表合并排序后依次 tryReadLock（见 StatementContext.java:888）。
